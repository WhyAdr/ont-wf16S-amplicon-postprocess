# `wf16s-postprocess` v0.4.3 Hardening and Fail-Closing Patch

**Audit target:** `WhyAdr/ont-wf16S-amplicon-postprocess` at commit
`3287d08e673c769b794b1f3376881ef876e8f2ec` (`VERSION` 0.4.2), audited
2026-09-07.

**Release verdict:** v0.4.2 closes most of the v0.4.1 audit, but the current
HEAD should not be treated as the final hardened state. The mandatory v0.4.3
work below addresses six confirmed correctness/reproducibility defects and
then closes the remaining transaction, manifest, and resource-boundary gaps.

This plan is implementation-ready. It deliberately preserves the current
scientific behavior: classified-only analytical denominators, explicit
unclassified accounting, the eight-rank lineage schema, Kraken direct/clade
arithmetic, direct-count Krona magnitudes, FAPROTAX 1.2.12 non-exclusive
function counts, current output names, and current statistical methods. No new
biological analysis is introduced.

---

## 1. What v0.4.2 successfully fixed

The following v0.4.1 findings are closed and must not be regressed:

- the release verifier now expects the complete eight-module registry and
  accepts canonical `not_run` records for unrequested modules;
- runner cleanup is inside `main()`, so ordinary R errors unwind through
  `on.exit()`;
- failed-module writes are rolled back before a failed new run is published;
- completed prior output is retained when an overwrite run fails;
- legacy output ownership is derived conservatively or rejected;
- Python and R now agree that read IDs are unique per assignment file and that
  read length must be positive;
- the source digest ignores generated Python bytecode;
- NCBI refresh checks exact name, rank, and ancestor presence before accepting
  a newly queried TaxID;
- beta resampling has a minimum-success fraction;
- whitespace checks no longer always select `HEAD` as their comparison base.

Python's ten resolver tests pass at the audited commit, as do Python source
compilation and `git diff --check`. R was not installed in the audit
environment, so the R/testthat and end-to-end assertions below remain required
release evidence rather than assumed-green checks.

## 2. Mandatory v0.4.3 findings

### P1-1 — Refresh rollback conflicts with the final immutability check

**Evidence**

`analysis/00_run_pipeline.R` restores the source taxonomy cache after any
failed refresh-mode run. Restoration uses `atomic_replace()`, which creates a
new filesystem entry and therefore changes the cache mtime. The subsequent
pre-publication call uses `allow_taxonomy_cache_change = FALSE` whenever
`any_failed` is true. `assert_inputs_unchanged()` then compares path, size,
mtime, and SHA-256 against the original inventory.

Therefore, a controlled byte-for-byte rollback is classified as an unexpected
input mutation. Even a failure that occurred before Kreport changed the cache
can trigger the problem, because the runner rewrites the original bytes
unconditionally. On a new output root, the error occurs before publication and
can remove the failed-run manifest that should have been the explicit commit
record.

**Required change**

- Replace the Boolean `taxonomy_cache_committed` model with an explicit state:
  `unchanged`, `candidate_committed`, or `restored`.
- Record the original SHA-256, size, mtime, and mode. Before restoring, hash the
  current cache; if it already equals the original SHA-256, do not rewrite it.
- Treat content identity (`canonical path + size + SHA-256`) as the scientific
  immutability invariant. Retain mtime as provenance, but do not reject a
  controlled byte-identical restoration solely because its mtime changed.
- If restoration was necessary, verify its SHA-256 before allowing either a
  failed manifest or the previous completed tree to remain authoritative.
- Store the backup as a temporary file rather than holding the entire cache in
  an R raw vector.

**Tests**

Add process tests for refresh mode in which:

1. a module fails before Kreport touches the cache;
2. Kreport commits a candidate and a later module fails;
3. Kreport is failure-injected after writing;
4. each case preserves byte-identical source-cache content;
5. a new output root publishes a valid failed manifest;
6. an overwrite retains the byte-identical previous completed run.

### P1-2 — Concurrent taxonomy refresh can silently overwrite another update

**Evidence**

The resolver verifies the source cache immediately before and after its initial
read, but online queries can then take seconds or minutes. Immediately before
`os.replace()` commits `candidate_cache`, it does not verify that the source
cache still has `source_cache_sha256_before`, and it holds no interprocess
lock. A second writer can update the cache during NCBI queries and that update
is silently lost.

This was reproduced by mutating the cache from a mocked query callback: the
resolver returned success and removed the external entry.

**Required change**

- Add a cross-platform exclusive cache lock held from the final pre-read
  verification through commit. A small standard-library context manager may
  use `fcntl.flock()` on POSIX and `msvcrt.locking()` on Windows; do not add an
  unpinned Python dependency.
- Store lock-owner diagnostics (PID, hostname, UTC start time) in the lock file
  after acquisition. Apply a bounded timeout and fail with
  `E_TAXONOMY_CACHE_BUSY`; never break an apparently live lock automatically.
- Re-hash the source cache immediately before `os.replace()`. If it differs
  from the initially accepted hash, abort with `E_TAXONOMY_CACHE_CHANGED` and
  preserve both the external revision and the run-local candidate.
- Reject repeated `--expected-input` specifications for one path when their
  hashes disagree.

**Tests**

- Mutate the cache during a mocked NCBI query and assert non-zero exit plus
  preservation of the external bytes.
- Run two resolver processes against one cache and assert that one waits or
  fails cleanly rather than overwriting the other.
- Exercise the lock on Linux and Windows CI.

### P1-3 — Output publication has no same-root concurrency guard

**Evidence**

Two pipeline processes can validate the same output root, build independent
stages, and both enter `publish_staged_run()`. With no output lock, the later
process can rename the first process's newly published result to its own
backup and silently replace it. The final manifest remains internally valid,
but one completed run disappears without an ownership or busy error.

**Required change**

- Acquire an exclusive output-root lock before `validate_prior_output()` and
  hold it through manifest validation, publication, and cleanup.
- Put the lock beside the final directory, not inside it, so directory renames
  cannot detach the lock. Derive its name from a collision-resistant digest of
  the canonical final path.
- Prefer the cross-platform R package `filelock`; add it to runtime
  dependencies and `renv.lock`. Use a bounded wait and emit
  `E_OUTPUT_BUSY` with the target path.
- `--validate-only` need not acquire the output lock because it must not
  publish.

**Tests**

Launch two real R processes at the same output root. Hold the first at a
test-only barrier, assert the second fails or times out with `E_OUTPUT_BUSY`,
then release the first and verify one complete manifest/tree.

### P1-4 — Module-returned warnings are still discarded

**Evidence**

`run_beta()` now returns `warnings = beta_warnings`, but the runner later does:

```r
result$warnings <- unique(warnings)
```

Here `warnings` contains only conditions intercepted by the runner's outer
handler. Internally caught and returned beta warnings are overwritten. The
v0.4.2 changelog claim that statistical warnings propagate to module and run
manifests is therefore false.

**Required change**

Merge, validate, and retain both channels:

```r
returned_warnings <- result$warnings %||% character(0)
if (!is.character(returned_warnings) || anyNA(returned_warnings)) {
  # convert the module result into a contract failure
}
result$warnings <- unique(c(returned_warnings, captured_warnings))
```

Do not use the same variable name for the condition buffer and the manifest
field.

**Tests**

- Inject a warning that `run_beta()` catches internally and returns; require it
  once in `modules.beta.warnings` and once in the deduplicated run warnings.
- Inject an ordinary emitted warning and verify identical propagation.
- Reject `NA`, scalar non-character, or list-valued module warnings.

### P1-5 — Krona preflight defeats the documented TSV-only fallback

**Evidence**

The README and `run_kreport()` say that when `render_html: true` but
`ktImportText` is missing, the pipeline keeps Krona TSV output, records
`html_status = "renderer_missing"`, and emits a warning. In contrast,
`run_module_preflight()` raises `E_KRONA_PREFLIGHT` before execution whenever
the renderer is absent. With the default `render_html: true`, `--krona` is
therefore unusable unless KronaTools is installed.

**Required change**

- Preserve the established optional-renderer semantics. Missing
  `ktImportText` is a preflight capability warning, not an error.
- Return preflight warnings to the runner and include them in validation output
  without duplicating the execution warning in final manifests.
- Continue to fail if a located executable is not a regular executable file,
  or if an invoked renderer exits non-zero or produces no HTML.

**Tests**

- `--validate-only --modules kreport --krona` succeeds without KronaTools and
  reports TSV-only capability.
- The real run completes, publishes TSV and provenance, records
  `renderer_missing`, and claims no HTML.
- A fake renderer returning non-zero fails transactionally.

### P1-6 — `--validate-only` writes bytecode and overstates refresh prediction

**Evidence**

Kreport preflight invokes `python -m py_compile`, which necessarily writes an
`__pycache__/*.pyc` file. Thus the runner prints “Zero filesystem mutations
performed” even though a clean checkout is modified. CI misses this because it
already runs `compileall` and checks only whether the requested output
directory exists.

In addition, refresh-mode preflight without `--online-preflight` returns success
as soon as it sees unresolved nodes that would require NCBI. A later real run
can then fail on credentials, connectivity, ambiguity, rank, ancestry, or
remaining unresolved nodes. This violates the predictive-validation contract.

**Required change**

- Replace `py_compile` with a no-write syntax probe, for example a Python
  `ast.parse()`/`compile(..., mode="exec")` command reading the source bytes.
- Use `renv::load(project = repo_root)` for an already restored environment;
  do not call a project-mutating activation routine during validation.
- Snapshot the repository, configured inputs, taxonomy cache, and output parent
  before/after process-level validation tests and require no created, removed,
  or changed paths.
- For `--validate-only --refresh-taxonomy`, fail closed with
  `E_ONLINE_PREFLIGHT_REQUIRED` when unresolved nodes remain and online
  preflight was not explicitly permitted. Do not print `PASSED` for an
  indeterminate external dependency.
- Online preflight must use the same query, rank, ancestry, ambiguity, and
  unresolved-policy logic as execution. Document that it validates the service
  at that moment; it cannot guarantee future network availability.

## 3. Environment and provenance corrections

### P2-1 — External-CWD environment loading is not self-sufficient

The runner calls `requireNamespace("renv")` before it knows the project library.
An absolute-path invocation from outside the repository can therefore fail
even when the project's restored library contains `renv`. The current process
test inherits the already activated parent test environment and is not a clean
simulation.

Implement one non-mutating project-load helper shared by
`00_run_pipeline.R` and `install_packages.R`. It must locate the repository from
`--file`, load the committed renv bootstrap/project library, and provide a clear
`E_RENV_NOT_RESTORED` instruction when restoration is required. Test it in a
sanitized external process with `R_PROFILE_USER`, `R_ENVIRON_USER`, `R_LIBS`,
`R_LIBS_USER`, and renv activation variables unset.

### P2-2 — “Synchronized” still allows packages from global libraries

`read_lock_status()` requires only that the project library occurs somewhere
in `.libPaths()`. Each package is resolved with `find.package()`, and a matching
version from a later global library is accepted. Consequently, a partly empty
project library plus matching global packages can still be labeled locked.

For a synchronized publication run, require every non-base locked package's
canonical location to be inside the canonical project library. Record global
fallbacks as `library_discrepancies`. Add a test that temporarily places a
matching-version package outside the project library and proves that the lock
status is `mismatch`.

### P2-3 — Startup files are absent from source provenance

The source digest and dirty-tree gate include `analysis/`, `config.example.yml`,
`VERSION`, and `renv.lock`, but omit `.Rprofile`, `renv/activate.R`, and
`renv/settings.json`. Those files can affect code before or during environment
loading while the manifest still reports a clean unchanged source digest.

Add all three files to the maintained tracked-source set and to the Git dirty
scope. Test that modifying each one changes the digest and sets `git_dirty`,
while creating ignored bytecode does neither.

## 4. Transaction and ownership hardening

### P2-4 — R `atomic_replace()` removes the valid target before rename

`atomic_replace()` unlinks an existing target and only then renames the temp
file. A rename failure leaves no target, so this is not atomic replacement.
The fallback branch in `write_manifest_v2()` has the same pattern.

- Never unlink the authoritative target before the replacement has a
  recoverable successor.
- Use a same-directory replacement primitive with documented Windows and POSIX
  behavior. If a true replace primitive is unavailable, use a lock plus
  target-to-backup / temp-to-target / verified-cleanup protocol and call it
  transactional rather than atomic.
- Preserve or deliberately set file mode; temp-file defaults must not silently
  change cache permissions.
- Verify the replacement's size and SHA-256 before deleting its backup.
- Consolidate manifest writing onto the same helper; remove the second unsafe
  implementation.

Inject failure at every transition and assert that either old or new valid
bytes remain available.

### P2-5 — Directory publication needs crash recovery

`publish_staged_run()` can be killed after `final_root` is renamed to a hidden
backup but before the stage becomes final. `on.exit()` handles ordinary R
errors, not SIGKILL, host failure, or power loss.

While holding the output lock, write a small sibling transaction journal with
canonical final/stage/backup paths and phases `prepared`, `prior_moved`, and
`stage_published`. On startup, recover deterministically:

- final missing + valid backup present → restore backup;
- final with valid manifest + backup present → retain final and remove backup;
- neither valid → fail with `E_OUTPUT_RECOVERY_REQUIRED` and preserve all
  evidence.

Journal writes themselves use verified replace semantics. Add subprocess tests
that terminate after each phase and validate recovery on the next invocation.

### P2-6 — Full-directory module snapshots scale quadratically

Before every module, the runner copies the entire accumulated stage—including
preserved user files and all earlier module products. Eight modules can copy
the same large tree repeatedly and fail from disk exhaustion before analysis.
Restoration also deletes the live stage before proving the snapshot can be
copied back.

Replace whole-stage snapshots with private per-module staging roots:

1. rebase the module's output configuration to an empty private root;
2. execute and validate there;
3. require the private-root file census to equal the module's declared output
   envelope;
4. merge only declared files into the run stage on success;
5. delete the private root on failure.

This makes rollback O(current module output), preserves unrelated files, and
also detects successful modules that silently wrote undeclared artifacts.

### P2-7 — Manifest ownership does not census every published file

The validator proves that declared owned files exist, but it does not prove
that every physical file in the staged tree is either owned or an explicitly
preserved unrelated file. A successful module can write an auxiliary file and
omit it from `outputs`; that file is still published outside manifest
ownership.

Have `preserve_unowned_outputs()` return an explicit relative-path array. Before
publication require:

```text
physical staged files
  == owned_outputs (except not-yet-written run_manifest.json)
   ∪ preserved_unowned_outputs
```

Reject overlaps and case-folded collisions. Add SHA-256 and size records for
every pipeline-owned artifact except the self-referential manifest.

## 5. Manifest v2 revision 2

v0.4.2 added mandatory environment fields and stricter module-state behavior
while retaining `schema_revision = 1`. A v0.4.1 revision-1 manifest does not
satisfy the v0.4.2 validator, so the same advertised revision currently denotes
two incompatible shapes.

For v0.4.3, keep `schema_version = 2` and bump `schema_revision` to `2`.
Add:

- `preserved_unowned_outputs`: always a JSON string array;
- `artifacts`: always an array of objects containing `relative_path`,
  `size_bytes`, `sha256`, and `producer_module` (nullable only for root metadata);
- complete environment fields, including canonical project library and package
  locations.

Strengthen `validate_manifest_v2()` or rename it
`validate_manifest_v2_revision2()` so that it enforces:

- exact `pipeline == "ont-wf16s-postprocess"`;
- scalar typing before `%in%`, path normalization, or other operations;
- non-empty unique samples and requested modules;
- required non-null abundance, params, and taxonomy-cache fingerprints;
- cohort metadata presence and assignment/bamstats IDs constrained to samples;
- real UTC timestamps, `end_time >= start_time`, and nonnegative finite
  durations;
- the exact eight-module registry;
- completed run: no requested `failed`/`not_run` records;
- failed + `keep_going = TRUE`: at least one failed record and no requested
  `not_run` records;
- failed + `keep_going = FALSE`: modules before the first failure are
  completed/skipped, the failed module is failed with zero outputs, and all
  later requested modules are `not_run`;
- `error` only for failed, `reason` only for skipped/not-run, and canonical null
  timing for not-run;
- `run_manifest.json`, `resolved_config.yml`, and `session_info.txt` present in
  ownership;
- exact equality between the physical file census and owned plus preserved
  files;
- every artifact contained beneath the canonical output root, physically
  regular, size/hash matched, and owned by exactly one producer;
- locked runs have empty discrepancy arrays and every package location inside
  the project library;
- `package_versions` agrees one-for-one with `environment.package_locations`.

Keep an explicit read-only validator for revision 1 solely for safe overwrite
migration. Do not silently reinterpret revision 1 as revision 2.

## 6. Additional scientific and resource fail-closing

### P2-8 — NCBI ancestors are checked as an unordered set

`validate_taxonomy_context()` currently converts returned lineage names to a
set. A response containing all expected names in the wrong hierarchy is
accepted. Compare expected ancestors as an ordered subsequence of NCBI
`LineageEx`; reject reversals and duplicate-name ambiguity. Add positive,
missing-ancestor, wrong-rank, wrong-name, and reversed-order tests.

### P2-9 — Exact integer counts need safe aggregate bounds

Each abundance cell is limited to JavaScript/R's exact-integer range, but a
per-sample column sum can exceed that range when many valid cells are added.
Without an aggregate `total` column, downstream read accounting can then lose
integer exactness.

After parsing counts, require every sample total and every checked row aggregate
to be `<= 9007199254740991`. Use exact-safe totals throughout Kreport/Krona and
replace `%d` diagnostic formatting for numeric counts with non-coercing integer
text such as `format(..., scientific = FALSE)` or `%.0f` after validation.

### P3-1 — Add aggregate workload budgets

Scalar caps alone do not bound products such as
`samples × samples`, `samples × permutations`, or
`taxa × resampling_iterations`. Before allocation, estimate:

- distance-matrix cells/bytes;
- permutation-matrix cells/bytes;
- rarefaction result rows;
- plot dimensions driven by sample/taxon cardinality.

Fail before output mutation with a stable resource error or require an explicit
development override. Do not change default analyses for ordinary cohorts.

### P3-2 — Isolate the failure-injection hook

`WF16S_INJECT_MODULE_FAILURE` is honored by production code whenever it exists
in the ambient environment. Require an additional explicit test-mode sentinel,
or inject the module runner as a function argument in tests. Production runs
must ignore or reject test-only control variables.

### P3-3 — Correct complete push-range CI

`GITHUB_EVENT_BEFORE` is not populated merely by referencing the push event; the
workflow must explicitly map `${{ github.event.before }}` into `env`. Current
push jobs therefore normally fall back to `HEAD^` and check only the final
commit of a multi-commit push.

- Use `fetch-depth: 0` for the job that validates a commit range, or explicitly
  fetch the selected base.
- Set one explicit variable:

```yaml
env:
  WF16S_DIFF_BASE: >-
    ${{ github.event_name == 'pull_request' &&
        github.event.pull_request.base.sha || github.event.before }}
```

- Pass that base to both whitespace checks. Validate it as a commit, handle the
  all-zero new-branch SHA, and use the empty tree only for a true root commit.
- Add Python tests using temporary Git repositories for root commit,
  multi-commit push, new branch, and pull-request base behavior.

## 10. Explicit non-goals

Do not use v0.4.3 to add differential abundance, UniFrac, phylogenetic tree
construction, PICRUSt2/Tax4Fun2, FAPROTAX2-db, new normalization methods, or
automatic Pavian rendering. Do not change classified/unclassified
denominators, Kraken/Krona count magnitudes, FAPROTAX function multiplicity, or
the current analytical output names. This release is about making the existing
answers transactionally trustworthy—not teaching the pipeline new biological
tricks while its seat belt is still being tightened.
