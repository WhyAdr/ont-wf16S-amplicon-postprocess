The current HEAD is much stronger, but I would not tag it yet. I audited commit \[`19f6851`](https://github.com/WhyAdr/ont-wf16S-amplicon-postprocess/tree/19f6851a1e7bc90b65092e5cbb74f6e023c19c29), and there are five release-blocking issues plus several worthwhile hardening items.



\## Release blockers



1\. \*\*P1 — The release verifier contradicts the manifest contract\*\*



&#x20;  The runner initializes manifest records for all eight modules, including unrequested FAPROTAX as `not\_run` (\[runner lines 159–161](https://github.com/WhyAdr/ont-wf16S-amplicon-postprocess/blob/19f6851a1e7bc90b65092e5cbb74f6e023c19c29/analysis/00\_run\_pipeline.R#L159-L161)).



&#x20;  The verifier expects exactly the seven default modules and then rejects every status except `completed` or `skipped` (\[verifier lines 63–78](https://github.com/WhyAdr/ont-wf16S-amplicon-postprocess/blob/19f6851a1e7bc90b65092e5cbb74f6e023c19c29/tests/verify\_release\_run.R#L63-L78)).



&#x20;  Consequently, the default integration run cannot pass its own verifier.



&#x20;  Fix the verifier to require the complete eight-module registry, with:



&#x20;  \* requested modules: `completed`, `skipped`, or `failed` as appropriate;

&#x20;  \* unrequested modules: exactly `not\_run`, with reason present and timing/output fields empty.



2\. \*\*P1 — Transaction cleanup is not actually registered\*\*



&#x20;  \[`on.exit()` is called at script top level](https://github.com/WhyAdr/ont-wf16S-amplicon-postprocess/blob/19f6851a1e7bc90b65092e5cbb74f6e023c19c29/analysis/00\_run\_pipeline.R#L131-L136). `on.exit()` belongs to the current function; at script top level there is no enclosing function whose exit can trigger it. This follows the documented “current function exits” behavior of \[`on.exit`](https://stat.ethz.ch/R-manual/R-devel/library/base/html/on.exit.html).



&#x20;  Unexpected errors after staging can therefore leave an orphan stage or an unrolled taxonomy-cache mutation.



&#x20;  Wrap execution in `main()`, register cleanup inside it, and have failures raise conditions or return a status. Call `quit(status = status)` only after `main()` has unwound—calling `quit()` from the transactional scope can bypass normal cleanup semantics.



3\. \*\*P1 — A failed first run can publish undeclared partial outputs\*\*



&#x20;  When a module writes files and then fails, its result is replaced with `outputs = character(0)`, but its files remain in the shared staging directory. If no previous output exists, the runner still publishes that stage and its failed manifest (\[lines 267–284](https://github.com/WhyAdr/ont-wf16S-amplicon-postprocess/blob/19f6851a1e7bc90b65092e5cbb74f6e023c19c29/analysis/00\_run\_pipeline.R#L267-L284)).



&#x20;  This creates physical files that are absent from both `modules.\*.outputs` and `owned\_outputs`.



&#x20;  Use per-module staging or snapshot the stage before each module and delete every newly created path on module failure. Add failure injection after the first and final write of each representative module.



4\. \*\*P1 — Overwriting v0.4.0 preserves stale module products\*\*



&#x20;  `validate\_prior\_output()` only checks `pipeline` and `output\_root`; it does not validate schema, state, or ownership (\[atomic\_io.R lines 33–49](https://github.com/WhyAdr/ont-wf16S-amplicon-postprocess/blob/19f6851a1e7bc90b65092e5cbb74f6e023c19c29/analysis/utils/atomic\_io.R#L33-L49)).



&#x20;  v0.4.0 manifests did not contain `owned\_outputs`. Therefore, during a v0.4.0 → v0.4.1 subset overwrite, all old module products are considered “unowned” and copied into the new run. The stale-output problem survives across the exact migration users are likely to perform.



&#x20;  Either:



&#x20;  \* reject manifests predating the ownership schema with a clear migration error; or

&#x20;  \* derive and validate legacy ownership from `modules.\*.outputs`, constrained beneath the prior output root.



5\. \*\*P1 — “Synchronized” still does not prove the active environment\*\*



&#x20;  The runner checks dependencies before explicit project activation. Repository `.Rprofile` activation is not reliable when `Rscript` is launched from another working directory—which the process tests explicitly do.



&#x20;  `read\_lock\_status()` then compares only the 15 direct runtime packages plus optional module packages against a 68-package lockfile (\[preflight.R lines 80–111](https://github.com/WhyAdr/ont-wf16S-amplicon-postprocess/blob/19f6851a1e7bc90b65092e5cbb74f6e023c19c29/analysis/utils/preflight.R#L80-L111)). Matching direct versions can therefore be reported as `synchronized` while transitive packages or active library paths differ.



&#x20;  Explicitly activate the project or prove that the active libraries belong to it. Validate the runtime dependency closure and record `.libPaths()` plus resolved package locations.



\## Additional confirmed defects



\* \*\*Python/R assignment parsers disagree.\*\* `seen\_read\_ids` is shared across all assignment files in Python, while R resets it per sample. I reproduced a valid repeated read ID across two sample files being rejected by Python. Python also accepts read length `0`, while R rejects it. Move `seen\_read\_ids` inside the per-file loop and require `0 < read\_length <= 2147483647`.



\* \*\*Source digests include generated and ignored files.\*\* `maintained\_source\_files()` recursively includes everything below `analysis/`. Running `compileall` created an ignored `\_\_pycache\_\_/ncbi\_taxonomy...pyc`, which is then incorporated into the digest without making `git\_dirty` true. The same commit can therefore produce different source digests. Use `git ls-files` when Git is available and a strict source-extension allowlist for source archives.



\* \*\*Input immutability remains observational rather than snapshot-based.\*\* The Python resolver independently rereads abundance, assignments, and cache files. A file could change between reads—or change and then revert between runner fingerprint checks—producing a mixed-revision result. Pass run-local snapshots or expected SHA-256 values into the resolver and verify them immediately before and after each read. Do not globally exempt the taxonomy cache during refresh; validate one explicitly expected hash transition.



\* \*\*Manifest validation remains too shallow.\*\* Input fingerprint fields, package-version records, top-level scalar types, exact module registry, and ownership/output relationships are not exhaustively checked. `command` is incorrectly required to contain unique strings even though command-line tokens may legitimately repeat. Every published pipeline-owned file should be declared, contained under the root, exist, and—ideally—have a recorded hash.



\* \*\*Output/upstream overlap checking should be fully symmetric.\*\* The dedicated upstream-root test only rejects output nested beneath upstream, not upstream nested beneath output. Include discovered bamstats and canonical/symlink-resolved paths in a bidirectional overlap check.



\* \*\*NCBI refresh accepts an exact-name TaxID without checking taxonomy context.\*\* ESearch uniqueness alone does not establish that the result has the expected rank or ancestry. Fetch the candidate record and validate its scientific name, expected rank at that lineage depth, and available ancestor context before committing it.



\* \*\*Beta stability still lacks a minimum-success rule.\*\* One successful iteration among many failures is marked `Completed`. Add a configurable or documented required success fraction/count. Statistical warnings captured and muffled inside beta outputs should also propagate into the module/manifest warning record.



\* \*\*Whitespace CI is ineffective on main pushes.\*\* Both checks calculate a merge base against `origin/main`. Once `origin/main == HEAD`, the checked range is empty. Use the pull-request base SHA for PRs and `github.event.before` for pushes, with a zero-SHA/full-tree fallback.



\## Tests still needed



The process tests named “keep-going” and “fail-fast” currently fail during Kreport preflight, so they no longer test runtime failure behavior. Before release, add process-level tests covering:



\* default and FAPROTAX manifest verification;

\* fail-fast and keep-going after an injected module write;

\* new output versus existing output rollback;

\* v0.4.0-to-current subset overwrite;

\* external-CWD project activation and transitive lock mismatch;

\* mutation during resolver reads;

\* Python/R assignment-parser conformance;

\* source digest stability before and after Python compilation;

\* malformed manifests and every status/cross-field combination.
